1. Executive Summary & Problem Context

High-stakes university coding competitions and hackathons frequently suffer from systemic operational bottlenecks: manual registration receipt tracking via messaging apps, uncoordinated competition start signals, accidental leakage of problem statements, code tampering or post-deadline commits, and arbitrary, non-standardized faculty grading.

The VSpark 2026 Web Competition Platform resolves these challenges through a centralized, resilient web architecture. It unifies candidate onboarding, team creation, automated fee slip verification, synchronized countdown scheduling, sensitive-file exclusion packaging, dual-cloud persistence (Supabase Storage + Google Drive API OAuth 2.0), flexible dual-mode rubric evaluations, and a live public leaderboard with real-time Olympic-style podium calculation.

6. Feature Breakdown (A to Z) — Part 1: Participant & Team Engine

6.1 Multi-Mode Registration & Team Provisioning

The platform accommodates both individual software developers and 2-member collaborative teams. When registering as a team:

  • Dual Account Creation: The backend automatically provisions two separate user accounts in Supabase Auth. Member 1 is designated team_role: "leader" (primary submitter), while Member 2 is designated team_role: "member".
  • Shared Team Linkage: Both accounts share an identical team_id (UUID), team_name, university, and status. Both members receive individual welcome emails and can sign in independently.
  • Proof of Payment Upload: Candidates upload bank/mobile wallet (JazzCash, Easypaisa, Meezan Bank) deposit slips. Uploaded receipts are validated for MIME type (JPEG, PNG, PDF) and stored in private buckets.
  • Title Casing & Input Formatting: All participant names, team titles, and universities are normalized with Title Casing; contact numbers are validated with phone patterns.

6.2 Live 120-Minute Gated Competition Workspace (/dashboard)

🔒 Time-Locked Challenge Access

The problem statement, markdown instructions, PDF download, and submission form remain completely locked until the competition start time or faculty manual override.

⏱️ Synchronized Countdown Timer

A real-time countdown banner displays the remaining duration (Hours : Minutes : Seconds), synchronizing continuously with the server clock to prevent local machine time tampering.

6.3 Client-Side Code Sanitizer & In-Memory Packager

Traditional upload systems fail on large codebases due to serverless execution limits (e.g., Vercel 10s–30s timeouts). VSpark implements a high-performance in-memory archive engine:

// In-Memory Sanitization Filter (src/lib/competition.ts) const EXCLUDED_PATTERNS = [ /(^|[/\\])\.git([/\\]|$)/i, // Git internal tracking objects /(^|[/\\])node_modules([/\\]|$)/i, // Node package dependencies (heavy) /(^|[/\\])\.next([/\\]|$)/i, // Next.js build output cache /(^|[/\\])\.env(\..+)?$/i, // Environment variables & private keys /\.(pem|key|id_rsa)$/i // Cryptographic certificates & private keys ];

The JSZip engine traverses the selected directory, evaluates each relative path against the exclusion regex, and compresses clean source files into a single `.zip` file in under 1.2 seconds directly inside the candidate's browser memory before network transmission.

6.4 Triple-Redundancy Submission Pipeline

To eliminate the risk of lost submissions, VSpark requires and enforces a triple-redundancy architecture:

  1. GitHub Repository URL: Validated HTTPS link to the student's code repository with a 1-click prompt to add the faculty evaluator as a collaborator.
  2. Google Drive Project Folder: Student-provided shared folder containing runnable builds, live demonstrations, and documentation.
  3. Direct Source Archive (.zip): Clean, sanitized project archive stored in private Supabase Storage and mirrored to faculty storage.

Single Submission Finality: Enforced via PostgreSQL database constraints. Once submitted, the project is permanently locked against accidental overwrites or duplicate folders.

7. Feature Breakdown (A to Z) — Part 2: Faculty Admin Command Center

7.1 Unified Student & Team Management (/admin/students)

The faculty management console offers an intuitive interface for inspecting, verifying, and communicating with competition participants:

  • Team Deduplication: Instead of cluttering the interface with two separate rows for each 2-member team, the platform groups team members into 1 unified team entry (👥 Team: [Team Name]), displaying both Leader and Teammate credentials side by side.
  • Figma-Style Status Filters: Tabs for All Registrations, Teams (👥), Individual (👤), Pending Verification, Active / Approved, and Rejected, with live badge counts.
  • Student Detail Modal: Clicking any student/team row opens an expansive modal with:
    • Member 1 (Leader) Card: Name, email, phone with WhatsApp link, department, semester, and dedicated buttons: "Email Leader" and "Reset Leader Password".
    • Member 2 (Teammate) Card: Name, email, phone with WhatsApp link, department, semester, and dedicated buttons: "Email Teammate" and "Reset Teammate Password".
    • Shared Deposit Slip: Thumbnail preview with full-resolution receipt viewer.
    • Shared Submitted Code: GitHub repo link, Drive folder link, and ZIP download.
    • 1-Click Team Approval/Rejection: Approves or rejects both members simultaneously.

7.2 Faculty Evaluation Room & Dual-Mode Scoring (/admin/evaluations)

The evaluation module provides a flexible scoring system meeting all faculty grading workflows:

Option A: Direct Holistic Marks (0–100)

Evaluators can enter total marks directly via a numeric input field, adjust a smooth 0–100 range slider, or select 1-click quick presets (50, 60, 65, 70, 75, 80, 85, 90, 95, 100). Points are automatically distributed across the 9 rubric criteria.

Option B: Categorized 9-Criteria Rubric

Evaluators adjust granular sliders across all 9 official rubric categories (UI/UX 10, Auth 15, CRUD 20, Storage 10, API 15, Deployment 15, Code Quality 5, Docs 5, Defense 5).

Two-Way Mathematical Sync: Changes in the direct score update rubric categories proportionally; adjusting any individual category updates the total score in real-time. Evaluators can also append detailed qualitative feedback notes.

7.3 Master Competition Controls (/admin/settings)

  • Lifecycle Mode Switch: One-click toggles between scheduled, open, and closed states.
  • Challenge Task Markdown Editor: Real-time editor with live preview for updating competition instructions and uploading task PDF briefs.
  • Tech Stack & Bank Guidelines: Live configuration of allowed frameworks, submission checklist items, bank title, bank account number, and registration fee.
  • Public Results Publishing: Gated toggle that holds leaderboard results in draft state until the faculty authorises public release.

11. Key Engineering Challenges & Technical Resolutions

Problem 1: Google Drive 0-Byte Service Account Storage Quota

Challenge: Google Cloud imposes a strict 0-byte storage quota on Service Accounts targeting personal Google Drive accounts (@gmail.com). Attempts to upload student archives resulted in 403 The user's Drive storage quota has been exceeded errors.

Resolution: Engineered a custom OAuth 2.0 PKCE authentication flow. The faculty administrator connects their personal Google Drive account in one click. The resulting refresh tokens are encrypted using AES-256-GCM with authenticated initialization vectors (IVs) and persisted in PostgreSQL. File uploads stream directly into the administrator's authorized 15 GB Drive space, completely bypassing service account quota limitations.

Problem 2: Vercel Serverless Function 504 Gateway Timeouts

Challenge: Compressing large project source trees on the server side via Node.js streams frequently exceeded Vercel's 10-second free tier / 15-second serverless execution limits, causing 504 Gateway Timeout failures.

Resolution: Migrated archive creation to the client tier using in-memory JSZip compilation. Files are filtered and compressed in the candidate's browser in under 1.2 seconds. The server receives a clean, pre-packaged `.zip` binary in a single fast POST request (120ms response time), achieving 100% 200 OK reliability.

Problem 3: Team Duplication & Disjointed Faculty Actions

Challenge: Registering 2-member teams produced two separate student rows in the faculty table. Clicking on either row led to ambiguity regarding which member was the submitter and required redundant password resets and separate approval actions.

Resolution: Implemented smart team grouping and deduplication in the admin state layer. Each team appears as exactly 1 unified row (👥 Team: [Team Name]). The modal resolves both leader and teammate profiles, providing dedicated action buttons ("Email Leader", "Reset Leader Password", "Email Teammate", "Reset Teammate Password") while sharing deposit slips, project code, and team-level approval.

Problem 4: Dual-Mode Evaluation Scoring Synchronization

Challenge: Faculty evaluators required the flexibility to either enter a fast holistic score (e.g., 85/100) or adjust 9 individual criteria, but manual adjustments risked mathematical inconsistency between the total and category breakdown.

Resolution: Built a two-way reactive mathematical synchronization engine. When direct total marks are entered, the system calculates proportional point distribution across the rubric weightings; when any rubric category slider is tweaked, the total score automatically sums and synchronizes without precision drift.
